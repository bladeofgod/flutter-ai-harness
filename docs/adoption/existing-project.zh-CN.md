# 在已有工程中采用 Harness

[English version](./existing-project.md) · [采用协议](./AGENT_BOOTSTRAP.zh-CN.md)

目标仓库已经包含可识别的工程事实时使用本路径。目标是增强现有工程系统，而不是用 Flutter 参考架构替换它。

## 只读审计

在不改变状态的前提下检查：

1. 现有项目指令、Agent 文件、架构文档和所有权规则。
2. 语言、框架、Package 边界、生成代码和依赖方向。
3. 构建、格式化、Lint、测试、集成、发版和 CI 命令。
4. 当前 Git 状态和用户已有改动。
5. 安全边界、外部输入、凭据策略、原生权限和部署面。
6. 现有任务、Review、证据和文档实践。

审计期间不得在目标仓库中执行来源 Harness 脚本。

## 映射，而不是复制

每项 Harness 资产都必须选择一种处理方式：

| 处理方式 | 含义 |
| --- | --- |
| `adopt` | 概念已经适用，只需调整目标工程命名即可引入。 |
| `adapt` | 概念有价值，但必须按目标技术栈或现有约定重写。 |
| `omit` | 没有真实消费者、已有更强等价能力，或引入后会伤害目标工程。 |

方案必须明确覆盖项目契约、任务 Schema、Executor 路由、工作流、Agent 事实源、工具适配、质量门禁、CI、Review、证据和归档规则。

## 冲突处理

- 用户指令和目标仓库批准后的契约优先于来源 Harness 示例。
- 不得直接覆盖已有 `CLAUDE.md`、`AGENTS.md`、CI、Hook 或构建入口；必须解释合并策略并取得批准。
- 保留更强的已有检查，不得为了匹配参考仓库而降低标准。
- Flutter 不是目标工程真实消费者时，不引入 Flutter 专属平台、角色或命令。
- 不为了复刻参考目录而创建无消费者角色或抽象。

## 推荐实施顺序

1. 建立或更新目标仓库自己的项目契约。
2. 定义目标范围、work kind、Executor 路由和文档生命周期。
3. 只增加必要角色、工作流、Skill 和 Memory。
4. 从一份权威事实源生成工具专属发现适配。
5. 把关键架构和安全规则转换为可执行检查。
6. 将聚焦检查增量接入现有 Hook 和 CI。
7. 用一项小而真实的目标工程任务验证采用后的工作流。

完成条件是目标技术栈检查通过、冲突与省略项已有记录，并准确保留所有不可用环境和未验证项。
