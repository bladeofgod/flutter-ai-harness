# 使用 Harness 创建新工程

[English version](./new-project.md) · [采用协议](./AGENT_BOOTSTRAP.zh-CN.md)

目标目录中不存在可识别工程时使用本路径。空目录不代表可以复制 Flutter Demo，也不授权 Agent 在没有用户参与时自行选择技术栈。

## 先讨论产品，再讨论技术栈

Agent 应先理解产品结果，只追问会实质改变架构或交付方式的问题。根据实际范围讨论：

- 产品类型：移动 App、Web、后端、桌面应用、SDK、CLI 或多 Runtime 系统。
- 必须支持的目标端和兼容范围。
- 指定或禁止的语言、框架、数据库、云服务和部署环境。
- 原生能力、离线行为、认证、支付、实时通信和受监管数据。
- 团队经验、维护周期、发布流程和运维约束。
- 测试深度、CI、安全审查、可观测性和发版证据要求。

Agent 应提出少量完整可行的技术栈选项，解释取舍、给出推荐并记录未决问题。此时仍不得初始化项目。

## 批准门禁

以下内容获得用户批准前，实施保持阻塞：

1. 产品范围和明确非目标。
2. 目标平台或 Runtime。
3. 技术栈和依赖策略。
4. 初始架构和所有权边界。
5. 构建、测试、CI 和发版验证方式。
6. 文件与目录初始化方案。

## 同时建立工程与 Harness

批准后：

1. 初始化能够证明所选技术栈的最小真实应用或服务。
2. 使用已确认事实建立目标仓库自己的项目契约，不继承参考 Demo 假设。
3. 定义目标技术栈对应的任务范围、Executor、工作流和质量门禁。
4. 只增加首批真实消费者需要的 Agent 角色和 Skill。
5. 建立一份 Agent 权威事实源，并生成目标工具支持的适配。
6. 将格式化、分析、测试、构建和 CI 接入已选择的工具链。
7. 用一项小而真实的任务验证初始化结果，并保留真实证据。

不得预填空架构层、虚构任务历史，或在没有真实消费者时增加集成。最终仓库应能说明每个初始依赖、角色和门禁存在的理由。
