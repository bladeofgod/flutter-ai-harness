工程指南 / 参考实现

让 AI 生成的代码进入工程系统。

Flutter AI Harness 将项目约束、专业角色、任务产物、审查闭环和质量门禁 变成仓库自身的基础设施，面向 Flutter 与长期维护的原生宿主工程。

查看代码仓库 选择采用方式
1 个事实源 Claude 项目资产保持权威
2 个原生宿主 Android 与 iOS 始终是一等构建目标
1 个通宵 参考 Demo 在执行阶段无人干预完成
不是运行时 SDK

可以 Clone、研究或改造成自己的工程模式，但不要把它理解为 Package， 也不要把它当成按版本依赖的应用组件。

01 / 为什么需要

代码生成只是交付过程的一部分。

AI 可以很快生成页面、API Client 或测试，但生产质量依然取决于代码应该放在哪里、 必须保护哪些契约、什么证据能够证明它有效，以及由谁独立审查最终结果。

Harness 是归仓库所有的工程环境：为 Agent 提供足够的上下文和验证工具， 同时保留清晰边界，让结果能够执行、审查和追溯。

缺少 Harness 时

项目知识散落在对话历史和个人记忆中。Agent 可以生成代码，但 Package 边界、 测试范围、原生端一致性和完成条件仍然是隐含的。

具备 Harness 后

长期契约与代码一起维护。任务承载可执行范围，角色保持聚焦，检查产生证据， Review 问题在归档前返回实现闭环。

02 / 系统模型

一套项目契约，适配多个执行工具。

仓库以 Claude 为优先事实源。.claude/ 下的 Command、Agent、 Skill 与 Memory 保持权威；Codex 原生 Skill 和自定义 Agent 由同一套资产生成， 并通过门禁检查漂移。

权威事实层

CLAUDE.md 定义项目不变量；.claude/ 维护工作流、角色、聚焦 Skill 与低频长期经验。

确定性生成并校验

Codex 适配层

AGENTS.md、.agents/skills/ 和 .codex/agents/ 提供原生发现能力，但不成为第二份项目契约。

第 01 层 契约

架构、依赖方向、原生规则和安全策略。

第 02 层 上下文

任务卡、Figma 上下文、按需 Skill 和 App 文档。

第 03 层 执行

专业 Agent 负责实现、测试、审查和运行 App。

第 04 层 证据

质量检查、Review 报告、脱敏日志和归档决策。

apps/demo -> app_features, app_data, app_im, app_core, app_ui
app_features -> app_data, app_im, app_core, app_ui
app_data / app_im -> app_core
app_core / app_ui -> 不依赖其他 Workspace Package

03 / 专业角色

职责越聚焦，独立判断越可靠。

角色不是装饰性的身份设定。每个 Agent 都有明确职责、工具范围、停止条件和输出契约， Reviewer 不继承执行者的上下文偏见。

任务规划

Architect

将产品、设计和仓库证据转成可独立执行的任务。

不实现应用代码。
功能实现

Task Executor

按已批准的单张任务卡实现功能、测试和聚焦验证。

不重新定义架构，也不自我批准。
原生边界

Bridge Engineer

按契约优先方式维护 MethodChannel 和 EventChannel。

必须保持 Android 与 iOS 行为一致。
正确性

Reviewer

检查行为、架构、生命周期、契约漂移和测试缺口。

首轮审查只读，不修改实现。
安全性

Security Reviewer

追踪信任边界、敏感数据、不可信输入和执行能力。

没有 Bash 或写入工具，Codex 使用只读沙箱。
运行证据

App Operator

通过 Marionette 对批准的 UI 行为 Spec 执行运行态验证。

由人独立安排，不属于任务默认门禁。

04 / 交付闭环

产物跟随任务流动，而不是围绕任务堆积。

常规闭环保持紧凑。人工参与集中在产品决策和高风险边界，Agent 在执行过程中 自动选择聚焦检查并完成独立审查。

标准化输入

读取产品规则、仓库契约和 Figma 节点。无法确认的行为明确记录， 不通过猜测补全。

拆分任务

创建命名唯一的任务卡，声明依赖、执行角色、实现范围、测试， 并按风险标记 Security Review。

实现与验证

修改最小有效范围，在同一批次补充测试，并通过证据采集器一次性保存 已脱敏的命令输出。

独立审查

普通 Reviewer 始终检查正确性；只有任务或实际 diff 改变安全边界时， Security Review 才加入流程。

修复与复审

P0、P1 阻断任务完成。修复返回原 Reviewer，跨维度修改会同时触发 普通与安全复审。

归档证据

只有检查、Review、依赖关系和必要摘要全部有效后，任务才移动到 docs/tasks/done/。

05 / 安全审查

按风险触发、保持独立、绑定证据。

普通 UI 和说明文档不会增加额外门禁。只有任务改变信任、数据、原生、 供应链或 Agent 执行能力边界时，Security Review 才会启动。

  • 认证、会话、授权或用户数据隔离
  • 凭据、隐私数据、日志或安全存储
  • 网络、文件、Deep Link、WebView 或不可信反序列化
  • 平台通道、原生权限或宿主配置
  • 第三方依赖、Action、构建脚本或生成链路
  • Agent 工具、MCP、CI 权限、提交或发布能力

两种审查模式

任务门禁报告记录审查过的仓库文件并保存实现摘要，文件发生变化后旧报告自动失效。 独立审查可以直接检查用户提供的代码而不绑定文件，但不能作为任务归档凭据。

确定性控制

Schema 检查会拒绝非法任务元数据、缺失报告、过期摘要、不安全 Reviewer 工具 和发生漂移的 Codex 适配。

Agent 判断

每条发现都必须给出攻击者可控入口、受影响资产、危险操作路径、具体证据 和最小修法。

06 / 参考 Demo

仓库提供真实证据，而不是空白占位。

Shoppe 风格 Flutter Demo 使用确定性本地数据，覆盖认证、商品目录、搜索、 商品详情、购物车、结算、个人中心、设置、奖励、订单和客服流程。

开发记录：Demo 在一个通宵内完成，执行阶段没有人工介入实现。人工输入仅负责 选择设计稿、确认范围和处理环境授权。

07 / 采用方式

复用工程模式，不必复刻目录结构。

这套仓库刻意保持可改造性。采用目标是保留明确契约和反馈闭环，同时允许目标工程 延续自己的技术栈、Package 边界、CI 和团队约定。

01

运行参考工程

Clone 仓库并运行 Demo，检查任务历史和质量门禁，把它作为完整工程模式的 可执行示例。

02

改造现有项目

先让 Agent 对比 Harness 和目标仓库，识别冲突并生成适配方案，再选择性迁移 契约、角色、Command、Skill 与检查工具。

03

拥有最终结果

完成适配后，目标仓库自己的项目契约成为权威。上游后续变化只是可评估输入， 不是必须机械升级的版本依赖。

适配检查清单

  • 映射 Package 与 Feature 边界
  • 识别原生宿主职责
  • 选择权威 Agent 事实源
  • 区分生成适配与工程事实
  • 只保留存在真实消费者的角色
  • 把关键规则转换为可执行检查
  • 定义证据和归档路径
  • 在外部边界保留人工控制

08 / 能力边界

Harness 明确不承诺什么。

清晰的非目标可以避免参考架构演变成携带大量无效复杂度的万能框架。

不是运行时 AI

不会给 Flutter App 增加 AI 功能。

Harness 作用于工程仓库和开发流程。

不是 Package 契约

不通过依赖版本接入。

团队需要阅读、抽取并改造成自己的工程模式。

不编造产品事实

Agent 不会补全缺失的产品决策。

会改变用户行为的歧义必须回到人工确认。

不默认自动化一切

UI 操作由人独立安排。

App Operator 报告不会被静默加入普通任务门禁。

不伪造平台一致性

静态检查不能替代原生构建。

Android 和 iOS 始终是明确的契约与构建目标。
